# ZuriMart Terraform Standards

**Project:** PROJECT ZURI PULSE  
**Phase:** 2  
**Step:** 3  
**Status:** ACTIVE

## 1. Purpose

This document defines the standards for all Terraform code in the ZuriMart multi-cloud landing zone.

These standards apply to:

- AWS
- Azure
- GCP
- Dev
- Staging
- Production
- DR
- Bootstrap/state infrastructure

## 2. Repository Layout

All Terraform code lives under:

```text
infra/terraform/

```

# The main directories are:

infra/terraform/
├── modules/
├── environments/
├── global/
├── backends/
├── bootstrap/
├── scripts/
└── policies/


## 3. Module Rules
Every reusable module must include:

versions.tf
variables.tf
main.tf
outputs.tf
README.md



# Modules must:


Use snake_case for all variables and outputs.
Include descriptions for every variable and output.
Use validation blocks where values are constrained.
Avoid hardcoding environment names, project names, or cloud-specific values.
Accept standard tags from the global tags module.
Accept standardized names from the global naming module.


## 4. Environment Strategy

Terraform workspaces are not used for environment separation.
Instead, environments are separated by directory and state file:


environments/dev/networking
environments/dev/security
environments/dev/kubernetes
environments/dev/databases
environments/dev/monitoring


The same pattern applies to staging and production.

This provides:
Clearer blast-radius control
Simpler backend configuration
Easier pull request review
Safer production operations



## 5. State Strategy
Each environment and layer has its own Terraform state file.

Example AWS backend key:

zuri-platform/dev/networking/terraform.tfstate

Example Azure backend key:

zuri-platform/dev/networking/terraform.tfstate

Example GCP backend prefix:

zuri-platform/dev/networking


Backend .hcl files are generated locally and ignored by Git.




## 6. Naming Convention 

Standard resource names follow:

<project>-<environment>-<cloud>-<layer>-<resource_type>-<suffix>

Examples:

zuri-platform-dev-aws-net-vpc
zuri-platform-staging-aws-k8s-eks
zuri-platform-production-az-k8s-aks
zuri-platform-dev-gcp-k8s-gke
zuri-platform-production-aws-db-rds


The global naming module must be used wherever possible.



## 7. Tagging Strategy

Project
Environment
Owner

ManagedBy

## 9. Variable Standards

Variables must:
Use snake_case.
Have a description.
Have a type.
Use validation blocks where appropriate.
Avoid secrets.
Use sensible defaults only for non-sensitive values.

Example:

variable "environment" {
  description = "Deployment environment."
  type        = string
}








## 10. Output Standards

Outputs must:
Use snake_case.
Have a description.
Expose only the values required by consumers.
Never expose secrets.

Example:

output "vpc_id" {
  description = "ID of the VPC."
  value       = aws_vpc.this.id
}


## 11. Plan and Apply Process

All infrastructure changes must follow this process:

Create a feature branch.
Make Terraform changes.
Run formatting and validation.
Run terraform plan.
Attach plan output to the pull request.
Receive review approval.
Apply only after approval.
Verify resources and outputs.
Merge the pull request.

Emergency changes must be reviewed retroactively within 24 hours.
